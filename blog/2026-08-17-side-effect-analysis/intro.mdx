# Side-Effect Analysis 👀

*A compiler has to assume that any function call can change any memory. Native Image already knows better. This post is about handing that knowledge to Graal, and about the small model that tells us it is right.*

## The Call in the Middle

What does `demo` return?

```java
static class Counter { int value; int other; }
static class Logger { int count; }
static class Link { Link next; }

static void countInto(Logger logger, Link link) {
    if (link != null) {
        logger.count++;
        countInto(logger, link.next);
    }
}

static int demo(Counter counter, Logger logger, Link list) {
    counter.value = 5;
    countInto(logger, list);
    return counter.value;
}
```

It returns 5, and you didn't need to study `countInto` to know it.
It walks a list and bumps a `Logger`.
It never touches a `Counter`.

Graal can't see that.
A call that isn't inlined is assumed to write *any* memory, as I described in the [Graal memory post](/blog/2026/09/27/graal-memory/intro).
So after the call it loads `counter.value` again.
I built this with Native Image and counted: one load of `counter.value` is left after the call.

Then I gave Graal one extra fact: this call writes `Logger.count` and nothing else.
The load is gone.
The store and the call stay, and the program prints what it printed before.

*(`countInto` is recursive on purpose, so the inliner gives up and the call stays a call.
I also switched off Native Image's trivial inlining, because in a toy program everything else lands in `main`.)*

This post is about where that fact comes from, and why you can trust it.

## Effects as Values

How do you tell a compiler what a function touches?
Put it in the function's type.

```
f : arguments → result
f : world × arguments → world × result
```

The second `f` takes a `world` and hands one back.
The world stands for whatever the function may observe or change: I/O, memory, exceptions.
Haskell's `IO` is built this way.
Underneath, an `IO a` is a function from a token for the real world to a new token and an `a`.

Once the world is a value, order is a data dependency:

```
w1 ← io_write(w0, fd, 3)
w2 ← io_write(w1, fd, 4)
```

The second write needs `w1`, and only the first write makes one.
Nothing has to say "this statement, then that one".
It is the same kind of dependency as `x = a + b` followed by `y = x * 2`.

## Cutting the Heap

Memory is an effect too, so give it a token:

```
store : heap × ref × value → heap
load  : heap × ref → value × heap
```

With a single `heap`, every load, store and call sits on one long chain, and nothing can move past anything.
That is roughly where Graal stands at every call it doesn't inline.
(For plain loads and stores it does better, because it keeps a location per field.
Calls are what spoil it.)

So cut the heap into pieces, each with its own token:

```
c1 ← store(c0, counter.value, 1)    -- takes and returns the Counter.value token
l1 ← store(l0, logger.count, 7)     -- takes and returns the Logger.count token
```

Neither store needs anything the other makes.
There is no data path between them, so they can swap, like `a + b` and `c * d`.
Two operations on the same piece keep their order.

We start with the finest cut Java's types give us for free: **one piece per field**.
`Counter.value`, `Counter.other` and `Logger.count` are different memory whatever the references point to.
The price is that all `Counter` objects share `Counter.value`.
Arrays get a piece per element type, except that all arrays of references share one, because a `String[]` can pass for an `Object[]`.
Everything else, like the JDK's own fields, goes into a last piece, `*`.

One rule keeps the cut honest: **every location lives in exactly one piece.**
In none, and a store slips past the tokens.
In two, and operations on one location sit on different chains, look independent, and get swapped.

Here is what a cut buys:

```java
static void deadStoreOtherField(Counter counter) {
    counter.value = 1;   // dead
    counter.other = 7;
    counter.value = 2;
}
```

```
v1 ← store(v0, counter.value, 1)
o1 ← store(o0, counter.other, 7)
v2 ← store(v1, counter.value, 2)
```

With one `heap`, the store to `other` sits between the two stores to `value`, and you'd have to look inside it.
With a token per field, `v1` has one user: the next store to the same field.
Nobody can observe the 1, and we can see that without running any analysis.

## Use Every Token Once

Why not copy tokens around like any other value?
Because then the chain would mean nothing: two operations taking the same `w0` would be two futures of one world.
So a token is used **exactly once**, never copied and never dropped.
Rust's borrow rules are a close relative: at any moment there is at most one `&mut` to a place.

We enforce this with **SSU**, *static single use* form.
It is SSA with one extra rule: every value is *used* exactly once, not just defined once.
An ordinary value, like an `int`, may be needed twice, but the program has to say so with an explicit `dup`.
Tokens have no `dup`.
So every token has exactly one user, and "who sees this value?" is answered by following one arrow.
That is how we read the dead store above.

Branches need one more rule.
When an `if` splits the flow, the token goes into both arms.
It isn't a copy, because only one arm runs, so it is a `fork`.
When the arms merge, a `join` picks the token of whichever one ran, like a phi in SSA.

## What a Call Takes

A load or store knows its piece from the field it touches.
A call has to take the token of every piece the callee *might* touch, including everything the callee calls in turn.
That set is the method's **signature**.

We compute it by giving each method the pieces its own accesses touch, then adding its callees' signatures until nothing changes.
Recursion is fine.
The sets only grow, and there are finitely many pieces, so it must stop.

`countInto` reads `Link.next`, and reads and writes `Logger.count`.
Its recursive call adds nothing, so those two are its signature, and `demo` looks like this:

```
v1     ← store(v0, counter.value, 5)
n1, l1 ← countInto(n0, l0, logger, list)   -- Link.next, Logger.count
x, v2  ← load(v1, counter.value)
```

The load takes `v1`, straight from the store, so it must read 5.
With one `heap`, the call would sit in between.

Sometimes we don't know what a method does.
It may be native, the analysis may have found no target for a call, or the method may compute an identity hash or run a class initializer.
Such a method **touches everything**, and so does everyone who calls it.
Unknown is never assumed harmless.

That is sound, and not very precise.
In Are We Fast Yet (AWFY), a standard benchmark suite, 199 of the 459 methods of the program still touch everything.
Even if identity hashes, class initialization and locks stopped counting as effects, only 12 of those would be freed, because the rest also reach unresolved calls, native code and raw writes.

## Where the Facts Come From

Nobody has to write a new whole-program analysis for this, because **Native Image** already runs one.
It works out which methods are reachable, which methods each call may reach (even a virtual one), and which fields each method reads and writes.
We read the answers out.

A feature we added to Native Image does that for every reachable method, JDK included, and a separate tool computes the signatures.
Then the build hands Graal a **kill set** on each call: the list of places that call may write.
Where a call said `any()`, it now says `Logger.count`.
Graal's own phases do the rest.

Here is the twist.
We first wrote rewrite rules that optimize directly on the token form.
Given the same facts as kill sets, Graal's own phases removed at least as many loads, so the rules are archived.
The tokens do the job they are good at: they explain why the facts are sound.
The kill set is what we deliver.

How do we know the facts are right?
Every claim has a deliberately false twin.
Tell the compiler that a method writes nothing when it does, and the program prints a wrong answer or hangs.
Every false claim we tried broke its image, and every honest image printed what the JVM prints.

## What About Threads?

Everything above pretends there is one thread.
With more, we assume the program has no data races.
An **acquire** (entering a lock, reading a `volatile`) may let other threads' writes in, so Graal must not reuse a value it loaded before it.
A **release** (leaving a lock, writing a `volatile`) lets this thread's writes out, so Graal must not drop a store because a later one overwrites it.

Memory that only one thread can reach is exempt.
A lock on such an object protects nothing, so it can go.
Deciding which objects those are is called **thread escape**, and its claims have false twins too: say a shared lock is local, and updates get lost.

Removing such a lock made it 16 to 19 times cheaper, and a `volatile` write 8 times.
That is a micro-benchmark whose whole body is the lock, so don't read it as a speedup.
On real programs, nothing is gained.
AWFY has no lock of its own, and we could prove none local in javac at the default setting, in the 17,496 lock and `volatile` sites of PetClinic, or in the 11 servers of the Barista suite.

## Something You Can Use Today

You can do by hand what the kill set does for the compiler.
A local variable is not memory, so no call can change it.
The JDK does this in `ArrayList.forEach`:

```java
final Object[] es = elementData;
final int size = this.size;
for (int i = 0; modCount == expectedModCount && i < size; i++)
    action.accept(elementAt(es, i));
```

`action.accept` could be any code, and a call Graal can't inline is assumed to write any memory.
`es` and `size` are locals, so it can't touch them.
I haven't measured how much this is worth on plain Graal, so I won't promise you a number.

## What It Bought

Loads first.
On four small programs written to contain calls that write little, Graal leaves 12.5 to 32.5% fewer loads.
On AWFY it leaves 4.2% fewer at the default optimization level and 2.1% fewer at `-O3`.

Then time, and one clear win.
Queens takes 25.7 to 27.8% less time in all fifteen `-O3` builds we timed.
Its recursive `placeQueen` now writes only array elements, so four fields stop being reloaded in its loop (6 loads in loops become 0).
Graal also inlines the recursion differently, and we never separated the two.
At `-O2`, where Graal inlines less, the gain is 0.5%.

Why not more?
Most methods stay opaque, as above, and removing a load isn't the same as removing time.
Native Image has no callee-saved registers, so a value kept across a call lives on the stack, a store and a load where the plain image would just reload the field.
An image built to leave out every effect the facts can't name (unsound on purpose, as an upper bound) removes three times the loads, 6.7% against 2.1%, and isn't any faster.
And code placement alone moves a benchmark by 4 to 13% with identical instructions, which is why we time twelve builds and not one.

Kill sets also cost build time: 7 to 9% on AWFY, 13 to 15% on javac, and 44 to 55% on PetClinic.

So the honest number is the suite's.
Over twelve builds, AWFY came out 1.6% faster on average with kill sets, from 3.0% faster to 1.7% slower, and most of that is Queens.
